# Imports

## Filament CSV imports need a queue worker for THIS project — ps output is misleading
QUEUE_CONNECTION=database, and Filament's import action only enqueues Filament\Actions\Imports\Jobs\ImportCsv (one job per 100 rows) plus the completion notification. With no worker, the admin sees a successful upload and an imports row with processed_rows=0 forever — no error anywhere. Hit this 2026-09-21: a 351-row LenderProductImporter upload sat unprocessed for ~2h with 0 lender_products, while `ps` showed two `queue:work` processes that actually belonged to /home/administrator/Documents/fynn_on_live/fynn_on_version_1 (check /proc/<pid>/cwd before trusting them). Run the dev stack with `composer run dev` (= `php artisan dev`, which starts serve + `queue:listen` + vite), not a bare `php artisan serve`. To drain a backlog once: `php artisan queue:work --stop-when-empty`. Diagnose with: SELECT total_rows, processed_rows, successful_rows, completed_at FROM imports, plus COUNT(*) on jobs/failed_jobs. The queued ImportCsv payload carries its rows inline, so a backlog stays importable even after the uploaded CSV is gone from temp storage.

## LenderProductImporter runs files of up to 1000 rows synchronously, so no worker is needed
LenderProductImporter::getJobConnection() returns 'sync' when $this->import->total_rows <= SYNCHRONOUS_ROW_LIMIT (1000), and null (the default queue) above that. Filament reads it after total_rows is set, and handles the sync case, completed notification included. Measured on MySQL for the whole upload request with 351 rows: a first-time upload takes about 0.8s and 769 queries, roughly one insert plus one audit_logs insert per row. A re-upload of unchanged data takes 55 queries. Per importer instance, which lives for one chunk, it loads all lenders once and each loan product's existing offers once. ListLenderProducts sets chunkSize(500), so a typical file is one chunk. Offers created during the import go into the cache, so a lender repeated for the same product updates the offer instead of inserting a duplicate, and a test covers that. Never go back to per-row firstOrNew or firstOrCreate. On a live database with network latency, per-row queries were the main reason uploads felt slow. The live server (plain RHEL, no Docker) had no queue worker, and queued imports stayed at 0 rows forever. Files over the limit still need a worker, via a systemd unit on live and `composer run dev` locally. Apply the same override to any other importer whose files are small. The end-to-end test in tests/Feature/Filament/LenderProductImporterTest.php drives the real ImportAction via callAction('import', data: ['file' => UploadedFile, 'columnMap' => [...]]). The columnMap may only map headers the uploaded file actually has.
