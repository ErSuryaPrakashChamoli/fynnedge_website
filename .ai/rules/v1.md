# V1

## External bureau requests name the person, not a customer id; match by mobile, never across a different PAN
User decision (2026-10-17): the external CIBIL API takes name, mobile, PAN, gender and recorded consent, never a FynnEdge customer_id (ignored if sent). MatchCustomerForBureauRequest picks a customer whose verified_mobile or phone matches: same PAN on file first, then the portal account, then the newest. A customer with a different PAN on file is never chosen (another person sharing the phone). Otherwise it creates a customer. It never edits an existing customer and never activates a portal account. The controller authorises create/fetchFresh BEFORE matching, so an unauthorised client creates no customer. Requests are stored with channel 'external' (CibilController::channel(), from the route name).
